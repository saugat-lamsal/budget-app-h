THE ONE BIG CHOICE: SWITCHES, NOT DELETIONS

Upstream keeps changing: rule fixes, security updates, new screens. To
merge those in later, her repo has to stay close to upstream's code.
How:

1. Nothing of upstream's is deleted. The old card and the mom reserve
   stay in the code. Her setup turns them off with switches that are
   fixed on her setup day and are not on her Settings screen. Off means
   off: no reserve is ever taken, nothing about mom or the old card is
   offered in review, and no screen shows them. It is not the same as
   setting them to zero.
2. Upstream's defaults stay upstream's. DEFAULT_SETTINGS does not change.
   Her starting values live in a new file (packages/money/src/her-setup.ts)
   that her setup day starts from. Every upstream test runs on upstream's
   defaults and keeps passing untouched. Those tests are a guard on the
   shared code.
3. Each new setting gets the value that means "as upstream" for any
   history saved before it existed, as B242 taught: a saved setup day
   with no Wishlist share opens with Wishlist at 0%, one card, mom on,
   and no asking. history-check.test.ts's guard (SETTINGS_ON_HIS_SETUP_DAY)
   keeps proving his real history still opens.
4. Her additions go in new files wherever possible: her-setup.ts,
   wishlist.ts, statement.ts, her own test files, her own worked-example
   files (packages/money/worked-examples-h.txt and
   packages/server/worked-examples-h.txt), docs/her-*.txt. Shared files
   get small hooks only.
5. Database steps. Upstream adds steps to db/database.ts STEPS (one list,
   numbered by place). If her repo adds step 12 and upstream later adds
   its own step 12, the two can never be merged. So her tables go in a
   second list (HER_STEPS, its own version in a table her_schema), run
   after upstream's. Upstream's list is never touched, and its new steps
   merge in as they come.
6. Rule numbers. Her rulebook keeps every upstream number. Rules that do
   not apply to her are listed once as "Off in this setup" (their tests
   still run, on upstream's settings). New rules get numbers from 50 up,
   so upstream's new sections (43, 44, ...) never land on hers.
   test/every-rule-has-a-test.test.ts reads budget-app-rulebook.md, so her
   rulebook keeps that file name.

Not chosen: rewriting the code for four fixed accounts of hers. It would
be simpler code, but it would conflict with nearly every upstream change.

The plain-words explanation for her (it goes on the card's sheet in the
app and in her rulebook, with made-up numbers):

  "Why paying your card isn't spending. When you buy $30 of groceries on
  a card, the app takes the $30 out of Needs that same day. Your checking
  account still has the $30, because you haven't paid the card yet. So
  the $30 isn't in any bucket any more, but it's still in your account,
  waiting for the card bill. That's what "set aside" means. When you pay
  the card $30 from checking, checking goes down $30 and the card goes
  down $30, and no bucket changes, because the $30 was already counted on
  the day you bought the groceries. You don't have to work out the bill
  or save for it separately. If every purchase is sorted, the money for
  each card is already there."

KEEPING UPSTREAM: MERGING FIXES IN LATER

- git fetch upstream, then merge upstream/main into a branch of hers
  (never into main directly), as a pull request, with the full
  "SKIP_BROWSER_TESTS=1 npm test" and CI.
- CLAUDE.md, the rulebook, the roadmap, fly.toml and litestream.yml:
  always hers. Written down in full in docs/her-merging.txt (PR 1). In
  short:
  - .gitattributes (in git) names the five files with "merge=ours".
  - That line does nothing alone. Git only knows a merge driver called
    "ours" from local config, which is never in git. So every machine
    and every clone that merges upstream must run, once:
      git config merge.ours.driver true
    Without it, git ignores the line and merges or conflicts the files as
    usual. A wrong merge would bring his CLAUDE.md, his rulebook, or
    worse, his fly.toml (his app name) into her repo.
  - Merge on a machine with that config, never with GitHub's web buttons.
    GitHub's merge ignores local merge drivers.
  - After every merge, check that the five files did not change:
      git diff HEAD^1 HEAD -- CLAUDE.md budget-app-rulebook.md
        budget-app-roadmap.md fly.toml litestream.yml
    (empty means they are still hers).
  - Then read upstream's own diff of those files: a rule he changed may
    need the same change in hers, with the developer's OK.
- Code: should merge cleanly while the switches rule holds. A conflict in
  shared code means a hook grew too big. Fix it by moving her part into
  her own file.
- The Node update (PR #51, already in main): nothing to do now. The next
  one merges the same way.
- The push URL stays DISABLED. Nothing of hers ever goes to upstream.
